# ย้ายไฟล์แนบแชตเดิมไปพื้นที่ private

โค้ดรอบนี้เก็บไฟล์ใหม่ใน `chat-private-attachments` และออก signed URL สำหรับส่งให้ลูกค้า 7 วัน เจ้าหน้าที่เปิดประวัติได้ด้วยการออกลิงก์ใหม่ผ่าน RLS ส่วน bucket `chat-attachments` เดิมยังเป็น public เพื่อรักษาลิงก์ที่ส่งไปแล้ว จึงยังมีความเสี่ยงกับไฟล์เดิมจนกว่าจะทำขั้นตอนย้ายและปิด public

1. Deploy migration และ frontend/Edge ที่รองรับ private bucket/การ refresh signed URL ก่อน ตรวจเปิดไฟล์ใหม่ใน Omni-Chat และตรวจการส่ง LINE จากบัญชีทดสอบ
2. กำหนด `SUPABASE_URL` และ `SUPABASE_SERVICE_ROLE_KEY` ใน environment ของ terminal ที่เชื่อถือได้ ห้ามใส่ใน source/command output รัน dry-run: `node scripts/migrate-chat-private-attachments.mjs --manifest <local-private-backup.json>` สคริปต์อ่านทุกหน้าอย่างมีลำดับและบันทึก backup ของข้อความเดิมไว้ในเครื่อง ไฟล์นี้มีข้อมูลแชต ต้องเก็บในที่เข้าถึงได้เฉพาะทีมที่มีสิทธิ์
3. ตรวจ manifest และจำนวนไฟล์ จากนั้นรันคำสั่งเดิมเพิ่ม `--apply` สคริปต์คัดลอก bytes ไป private bucket โดยไม่ลบต้นฉบับ ตรวจ hash เมื่อมีไฟล์อยู่แล้ว ออก signed URL แล้วเปลี่ยนข้อความ/metadata เฉพาะแถวที่ยังเหมือน snapshot หากมีผู้แก้แชตระหว่างทำงานจะหยุดและแจ้ง conflict ไม่เขียนทับ
4. ตรวจประวัติข้อความ รูป และเอกสารทุกประเภทที่พบใน manifest รวมถึงข้อความที่มีหลายรูป หาก signed URL หมดอายุ frontend ต้องออกใหม่ได้ ปุ่มดาวน์โหลดต้องยังเปิดได้หลัง reload
5. **Boss jack ต้องอนุมัติวันหยุดใช้ลิงก์ public เดิมของลูกค้าก่อนปิด bucket** เพราะลิงก์เดิมใน LINE/Facebook ที่ส่งออกไปแล้วเปลี่ยนย้อนหลังไม่ได้ เมื่อตกลงแล้วจึงรัน `--apply --retire-legacy --accept-old-customer-links-expire` ข้อมูลต้นฉบับยังอยู่ครบ เจ้าหน้าที่ใช้ private links หลังย้ายได้
6. หากต้องย้อนกลับ ใช้ `--rollback --manifest <ไฟล์เดิม>` สคริปต์เปิด public bucket กลับก่อน แล้วคืนเฉพาะแถวที่ยังตรงกับสถานะที่สคริปต์ย้ายไว้ หากมีการแก้ภายหลังจะหยุดแจ้ง conflict และคงข้อมูลใหม่ของผู้ใช้ไว้

คำสั่งนี้ยังไม่ได้รันกับ production และไม่มีการแก้ข้อความหรือลบไฟล์จริง รอบนี้ทดสอบด้วย fixtures เท่านั้น การปิด public ของประวัติเดิมจึงเป็นขั้นตอน release แยกที่ยังต้องทำหลังอนุมัติวันเปลี่ยนลิงก์
