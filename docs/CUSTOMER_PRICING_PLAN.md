# แผนระบบราคาลูกค้า 4 แหล่ง

วันที่ยืนยันกติกา: 10 กันยายน 2026

ปรับแผน FlowAccount และ security gate: 13 กันยายน 2026

เอกสารนี้เป็นแผนพัฒนา ยังไม่เปลี่ยนราคาสินค้า ใบเสนอราคา หรือคำตอบของ AI ในระบบจริง

สถานะ branch วันที่ 13 กันยายน 2026: ทำ Phase 1 แล้วเฉพาะฐานข้อมูลกลาง, ราคาเน็ตใน Customer Profile, การตรวจราคาจาก Chatbot และใบเสนอราคาที่ Chatbot สร้าง พร้อม tests แต่ยังไม่ deploy หรือ apply migration ใน production ส่วนการ sync ประวัติจาก FlowAccount ยังปิดไว้จนกว่าจะยืนยันสิทธิ์และ contract ของ connector เป็นลายลักษณ์อักษร หน้าออกใบเสนอราคา Backoffice และ Storefront ยังใช้ logic เดิมและต้องย้ายมาใช้ resolver กลางใน phase ถัดไปก่อนประกาศว่าใช้ราคาเดียวกันครบทุกช่องทาง

## 1. กติกาที่ใช้เป็นแหล่งเดียว

ระบบต้องคำนวณแยกทีละสินค้า ไม่ใช้ส่วนลดรวมท้ายบิลเป็นผลลัพธ์หลัก

1. คำนวณ `base_price` จากราคาสินค้าหลังหักส่วนลดปกติที่ตั้งในคลัง
   - ส่วนลดแบบจำนวนเงิน: `base_price = max(0, price - discount_value)`
   - ส่วนลดแบบเปอร์เซ็นต์: `base_price = round(price × (1 - discount_value / 100), 2)`
2. ถ้ามีราคาเน็ตที่ยังใช้ได้สำหรับลูกค้า สินค้า และหน่วยนั้น ให้ใช้ `net_price` ทันที และห้ามหัก Tier ซ้ำ ราคาเน็ต CoreBiz ชนะเสมอแม้สูงกว่าประวัติ
3. ถ้าไม่มีราคาเน็ต ให้ใช้ราคาจากใบเสนอราคา FlowAccount ล่าสุดที่จับคู่ลูกค้า, SKU, หน่วย และจำนวนตรงทั้งหมด เฉพาะรายการที่ sync ตรวจ provenance/สถานะ/สกุลเงิน/ความสดแล้วว่า eligible
4. ถ้าไม่มีสองแหล่งแรกและลูกค้ามี Tier ให้คำนวณ `final_price = round(base_price × (1 - tier_percent / 100), 2)`
5. ถ้าไม่มีราคาพิเศษและไม่มีส่วนลด Tier ให้ใช้ `base_price`

ลำดับราคาเป็น `ราคาเน็ต CoreBiz → ประวัติ FlowAccount ที่ eligible → ราคา Tier จาก base_price → base_price` ทุกช่องทางต้องเรียกตัวแก้ราคาเดียวกัน

chat ที่ bot เพิ่งผูกลูกค้าจากเลขภาษียังใช้ได้เฉพาะ `base_price` จนเจ้าหน้าที่หรือหลักฐานสมาชิกที่ตรวจสอบแล้วอนุญาต personalized pricing เพื่อไม่ให้ผู้ส่งเลขภาษีของบริษัทอื่นเห็นราคาสัญญา, Tier หรือประวัติเดิม

## 2. ค่า Tier ตั้งต้น

คงเปอร์เซ็นต์ที่ใช้อยู่เดิมเป็นค่าเริ่มต้น และให้ owner/admin แก้ได้จากเมนู Tier เดิม

| Tier | ส่วนลดตั้งต้น |
| --- | ---: |
| ทั่วไป (`general`) | 0% |
| Silver | 2% |
| Gold | 3% |
| VIP | 5% |

การแก้เปอร์เซ็นต์ในอนาคตมีผลกับการคำนวณใหม่เท่านั้น ใบเสนอราคาที่ออกแล้วต้องเก็บราคาตาม snapshot เดิม

## 3. ตำแหน่งเมนู

เพิ่มหัวข้อ **ราคาและส่วนลด** ในหน้ารายละเอียดลูกค้า เพราะเจ้าหน้าที่ต้องเห็นก่อนว่ากำลังตั้งราคาให้ลูกค้ารายใด

หน้าจอนี้ต้องแสดง:

- Tier ปัจจุบันและเปอร์เซ็นต์ที่ได้รับ
- ราคาปกติในคลัง ส่วนลดปกติ และ `base_price`
- รายการสินค้า หน่วย ราคาเน็ต วันที่เริ่ม/สิ้นสุด สถานะ และหมายเหตุ
- ราคาที่ระบบจะใช้จริง พร้อมป้าย `ราคาปกติ`, `Tier`, `ประวัติ FlowAccount` หรือ `ราคาเฉพาะลูกค้า`
- วันเวลาที่สร้างและแก้ล่าสุด โดยไม่ส่ง UUID ผู้สร้าง/ผู้แก้ผ่าน staff RPC

การเพิ่ม แก้ ปิด หรือกำหนดอายุราคาเน็ตให้ owner/admin ทำได้ ส่วนพนักงานขายอ่านราคาที่อนุมัติแล้วได้ แต่แก้กติกาไม่ได้

## 4. โครงสร้างข้อมูล

สร้างตาราง `customer_product_net_prices` โดยมีอย่างน้อย:

- `customer_id`, `product_id`, `unit`
- `net_price` ชนิด `numeric` และต้องมากกว่า 0 (ของแถม/ราคา 0 ให้ใช้กติกาเฉพาะภายหลัง)
- `active`, `valid_from`, `valid_until`
- `note`, `created_by`, `updated_by`, `created_at`, `updated_at`
- unique active rule สำหรับลูกค้า+สินค้า+หน่วย; rule ที่หมดช่วงเวลาแต่ยัง active ต้องปิดก่อนสร้าง rule ถัดไป เพื่อไม่ให้มีราคาชนกัน

ราคาเน็ต CoreBiz ใช้กับทุกจำนวนของลูกค้า+สินค้า+หน่วยนั้น ส่วนประวัติ FlowAccount เก็บใน private schema และ match `source_quantity` แบบ exact เท่านั้น ราคาขายอัตโนมัติจากทั้งสองแหล่งต้องมากกว่า 0; ของแถมหรือรายการราคา 0 ต้องให้เจ้าหน้าที่จัดการด้วยกติกาเฉพาะ ตาราง cache ไม่เก็บ raw document, ที่อยู่, token, bank field หรือราคาทุน และไม่ถูกใช้จน sync สำเร็จพร้อมเปิด state อย่างชัดเจน แต่ละรอบ sync ต้องมี `sync_run_id` ใหม่ และ resolver ใช้เฉพาะข้อมูลจากรอบล่าสุดที่สำเร็จทั้งชุด เพื่อไม่ให้บรรทัดจากเอกสารที่ถูกยกเลิกหรือลบค้างเป็นราคาเก่า

เปิด RLS และ audit ทุกการเปลี่ยนแปลง ตารางดิบไม่เปิดให้ลูกค้าหรือ public อ่าน พนักงานอ่านผลจาก resolver ที่ผ่านสิทธิ์แทน

ก่อนเพิ่มตารางใหม่ต้องทำ migration ชดเชย schema ของ `products.discount_type` และ `products.discount_value` ให้ครบในประวัติ migration แบบ idempotent เพราะฐานจริงมีคอลัมน์และข้อมูลส่วนลดใช้งานอยู่ แต่ migration รุ่นแรกไม่ได้ประกาศคอลัมน์ทั้งสองไว้ครบ

## 5. Price resolver กลาง

สร้าง database function สำหรับรับ `customer_id` และรายการ `product_id` แล้วคืนข้อมูลต่อสินค้า:

- `list_price`
- `normal_discount_type`, `normal_discount_value`
- `base_price`
- `tier`, `tier_percent`
- `net_rule_id`, `net_price`
- สถานะว่ามี FlowAccount candidate ที่ eligible โดยไม่คืน raw document/cache reference ให้ Frontend หรือ AI
- `final_price`
- `price_source` เป็น `base`, `tier`, `flowaccount_quote` หรือ `customer_net`
- `resolved_at`

คำนวณด้วย `numeric` และปัดสองตำแหน่งใน resolver เท่านั้น Frontend แสดง preview ได้ แต่ห้ามเป็นผู้ตัดสินราคาสุดท้าย

## 6. จุดที่ต้องเปลี่ยนให้ใช้ resolver เดียวกัน

- หน้าออกใบเสนอราคาใน CoreBiz
- การแก้รายการใบเสนอราคาและคำสั่งซื้อ
- Storefront quote
- AI chat เมื่อค้นสินค้า ตอบราคา และสร้างใบเสนอราคา
- RPC ที่สร้างใบเสนอราคาจาก bot

AI ต้องรู้ `customer_id` ก่อนใช้ราคาเฉพาะลูกค้าหรือ Tier ถ้ายังยืนยันลูกค้าไม่ได้ ให้ตอบราคาทั่วไปจาก `base_price` และไม่เดาระดับลูกค้า

RPC สร้างใบเสนอราคาจาก bot ต้องผูก `customer_id` ก่อน resolve ราคา ไม่สร้างใบเสนอราคาแบบ `customer_id = null` แล้วค่อยผูกภายหลัง

## 7. Snapshot เอกสาร

เพิ่มข้อมูล snapshot ต่อบรรทัดใน `quote_items` และ `order_items` เช่น:

- `base_unit_price`, `unit_price`
- `price_source`, `tier_percent`, `net_rule_id`, `price_fingerprint`
- `pricing_snapshot`, `resolved_at`

ใบเสนอราคาใหม่เก็บส่วนลดอัตโนมัติไว้ในราคาต่อบรรทัด และไม่หัก Tier ซ้ำที่ท้ายบิล รายการในบิลเดียวกันจึงใช้ราคาเน็ตบางรายการและ Tier บางรายการได้ถูกต้อง

เมื่อ rule หรือ Tier เปลี่ยน ใบเสนอราคาที่ส่งแล้วไม่เปลี่ยนราคา หากยังเป็น Draft และเปลี่ยนลูกค้า ให้ resolve ใหม่พร้อมบันทึก audit และแจ้งเจ้าหน้าที่ก่อนแทนค่าราคาเดิม

## 8. ลำดับพัฒนา

1. ทำ migration ชดเชย schema เดิม แล้วสำรองและตรวจยอดข้อมูลส่วนลดสินค้า
2. เพิ่มตารางราคาเน็ต, private FlowAccount cache ที่ยัง disabled, RLS, audit และ resolver พร้อม unit/integration tests
3. เชื่อม bot quotation กับ resolver และ snapshot โดยไม่เปลี่ยน contract เดิม
4. ยืนยัน field contract/OAuth/quota ของ FlowAccount แล้วทำ sync แบบ idempotent; เอกสารที่ตีความราคา/ส่วนลด/VAT ไม่ชัดต้อง ineligible
5. เชื่อม Backoffice quotation และ snapshot ต่อบรรทัด
6. เชื่อม Storefront quote แล้วเทียบผลกับ Backoffice
7. เชื่อม AI price lookup กับ resolver โดยไม่ส่ง provenance ภายในให้ model/customer
8. เพิ่มหน้าจอ **ราคาและส่วนลด** ใน Customer Profile
9. ทดสอบด้วยบัญชีทั่วไป, Silver, Gold, VIP และลูกค้าที่มีราคาเน็ตแบบผสมหลายสินค้า ก่อนเปิดใช้จริง

## 9. เกณฑ์ตรวจรับ

- ส่วนลด Tier คิดจากราคาหลังส่วนลดปกติในคลังทุกกรณี
- ราคาเน็ตเฉพาะลูกค้าและสินค้าใช้ทับ Tier และไม่ถูกลดซ้ำ
- ราคาเน็ต CoreBiz ชนะราคาประวัติ FlowAccount แม้ราคา CoreBiz สูงกว่า
- ประวัติ FlowAccount ใช้ได้เฉพาะ customer+SKU+unit+qty ที่ตรง, THB, eligible, cache สด และเอกสารไม่เก่ากว่า revision ราคาสินค้า
- rule หมดอายุหรือปิดใช้งาน fallback ไป Tier แล้วจึงราคา base
- ค่า Tier ตั้งต้นคง 0%, 2%, 3%, 5%
- Backoffice, Storefront, AI และใบเสนอราคาให้ราคาเดียวกันสำหรับ input เดียวกัน
- ใบเสนอราคาที่ออกแล้วไม่เปลี่ยนเมื่อ Tier, ราคาในคลัง หรือราคาเน็ตถูกแก้ภายหลัง
- เงินและ VAT ปัดด้วยกติกาเดียว ไม่มี floating-point drift
- customer อื่น, staff ที่ไม่มีสิทธิ์ และ public อ่านหรือแก้ราคาเน็ตดิบไม่ได้
- chat ที่ผูกด้วยเลขภาษีแต่ยังไม่ยืนยันเห็นเฉพาะราคา base และไม่เห็น Tier/source/history
- การกดซ้ำหรือคำขอพร้อมกันไม่สร้างราคาเน็ตซ้อนกัน
- รายการ custom และค่าขนส่งยังใช้เส้นทาง manual ที่ระบุชัด ไม่ถูก resolver สินค้าปรับราคา

## 10. สิ่งที่ยังไม่ทำในรอบวางแผน

- ไม่แก้ค่า Tier หรือราคาสินค้าในฐานจริง
- ไม่ย้ายส่วนลดของใบเสนอราคาเก่า
- ไม่เปิดให้ AI ตอบราคาเฉพาะลูกค้าจน resolver, สิทธิ์ และ snapshot ผ่านการทดสอบ
- ไม่เปิด FlowAccount cache จน connector, line-price contract, eligibility และ complete sync ผ่านการตรวจสอบ
- ไม่ลบการคำนวณเดิมจนทุกช่องทางเทียบผลผ่านและมีแผนย้อนกลับ
